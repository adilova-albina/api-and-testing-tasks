# Задание 26 - Тестирование формы регистрации

Нужно протестировать форму регистрации. Основная задача — проверить обязательные поля, корректность email и ситуацию, когда такой email уже есть в системе.

## 1. Проверка обязательных полей

Для каждого обязательного поля нужно проверить, что произойдет, если пользователь его не заполнит.

Например:

| Тест                            | Ожидаемый результат                     |
| ------------------------------- | --------------------------------------- |
| Все поля пустые                 | Появляются ошибки у обязательных полей  |
| Одно обязательное поле пустое   | Ошибка показывается только у этого поля |
| Все обязательные поля заполнены | Форма проходит валидацию                |

Ошибки должны быть понятными пользователю, например:

```text
Поле обязательно для заполнения
```

## 2. Проверка email

Нужно проверить разные варианты email.

| Входные данные    | Ожидаемый результат            |
| ----------------- | ------------------------------ |
| `test@gmail.com`  | Корректный email               |
| `user123@mail.ru` | Корректный email               |
| `test`            | Ошибка                         |
| `test@`           | Ошибка                         |
| `@gmail.com`      | Ошибка                         |
| пустое значение   | Ошибка, если поле обязательное |

Проверку email желательно делать на frontend, чтобы пользователь сразу видел ошибку.

Но backend тоже должен проверять email, потому что frontend можно обойти.

## 3. Email уже существует

Отдельно нужно проверить ситуацию, когда пользователь вводит email, который уже зарегистрирован.

Например:

```text
Email: test@gmail.com
```

Если такой пользователь уже есть в базе данных, регистрация не должна создаваться повторно.

Сервер может вернуть:

```json
{
  "error": "EMAIL_ALREADY_EXISTS",
  "message": "Пользователь с таким email уже существует"
}
```

HTTP-код в таком случае может быть `409 Conflict`.

Пользователю нужно показать ошибку возле поля email.

## 4. Позитивный сценарий

Проверяем регистрацию с корректными данными:

```text
1. Открыть форму регистрации
2. Заполнить все обязательные поля
3. Ввести корректный email
4. Нажать «Зарегистрироваться»
5. Отправить запрос на сервер
```

Ожидаемый результат:

```text
Регистрация успешно выполнена
```

Сервер может вернуть `201 Created`.

## 5. Негативные сценарии

Также нужно проверить:

* пустые обязательные поля;
* неправильный формат email;
* email, который уже существует;
* слишком длинные значения;
* отправку некорректных данных напрямую на API;
* ошибку сервера.

Например, если сервер временно недоступен, пользователь должен увидеть понятное сообщение:

```text
Не удалось выполнить регистрацию. Попробуйте еще раз.
```

## 6. Какие тесты использовать

Я бы разделила тестирование на несколько уровней.

### Unit-тесты

Проверяют отдельную логику валидации:

```text
валидный email → true
невалидный email → false
пустое поле → ошибка
```

### Integration-тесты

Проверяют работу формы вместе с backend:

```text
Форма → API → база данных → ответ
```

Например, отправляем корректные данные и проверяем, что сервер создает нового пользователя.

### UI-тесты

Проверяют поведение самой формы:

* отображаются поля;
* отображаются ошибки;
* кнопка регистрации работает;
* после успешной регистрации открывается нужный экран.

## Итог

Главное проверить не только правильные данные, но и ошибки. Frontend нужен для быстрой обратной связи пользователю, а backend должен повторно проверять данные перед сохранением в базу данных. Это защищает систему от некорректных запросов и обхода frontend-валидации.
