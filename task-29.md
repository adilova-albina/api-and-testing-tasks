# Задание 29 - Регрессионное тестирование авторизации

Предположим, что была изменена общая библиотека авторизации, которую используют web- и mobile-приложения. После изменения нужно убедиться, что существующая авторизация продолжает работать.

## 1. Что нужно проверить

В первую очередь проверяем основные сценарии:

* вход с правильным логином и паролем;
* вход с неправильным паролем;
* вход с несуществующим пользователем;
* выход из аккаунта;
* получение и обновление токена;
* работу просроченного токена;
* доступ к защищенным страницам;
* права пользователей с разными ролями.

## 2. Тест успешного входа

```text id="6rj0qa"
1. Открыть страницу входа
2. Ввести правильные данные
3. Нажать «Войти»
4. Получить ответ от сервера
```

Ожидаемый результат:

```text id="l5l1td"
Пользователь успешно вошел.
Токен получен.
Открывается защищенная часть приложения.
```

## 3. Неправильные данные

Нужно проверить несколько негативных случаев:

| Сценарий                    | Ожидаемый результат                                      |
| --------------------------- | -------------------------------------------------------- |
| Неправильный пароль         | Ошибка авторизации                                       |
| Несуществующий пользователь | Ошибка авторизации                                       |
| Пустой логин                | Ошибка валидации                                         |
| Пустой пароль               | Ошибка валидации                                         |
| Просроченный токен          | Нужно выполнить повторную авторизацию или обновить токен |

Пользователь не должен получать доступ к защищенным данным при невалидном токене.

## 4. Проверка web и mobile

Так как библиотека используется в двух приложениях, тестирование нужно провести отдельно:

```text id="p9c1z4"
Общая библиотека авторизации
          ↓
     ┌────┴────┐
     ↓         ↓
   Web       Mobile
```

Нужно убедиться, что после изменения библиотеки оба приложения:

* могут выполнить вход;
* правильно сохраняют токен;
* отправляют токен при запросах;
* правильно обрабатывают истечение токена;
* выполняют выход из аккаунта.

## 5. Регрессионные тесты

Регрессионное тестирование нужно для того, чтобы новая версия библиотеки не сломала старую функциональность.

Основной чек-лист:

```text id="d9yrgq"
[ ] Вход работает
[ ] Выход работает
[ ] Неправильный пароль обрабатывается
[ ] Токен создается
[ ] Токен передается в API
[ ] Просроченный токен обрабатывается
[ ] Refresh token работает
[ ] Защищенные страницы недоступны без авторизации
[ ] Права пользователей работают
[ ] Web-приложение работает
[ ] Mobile-приложение работает
```

## 6. Какие виды тестов использовать

### Unit-тесты

Проверяют отдельные функции библиотеки авторизации:

* создание токена;
* проверку токена;
* обработку ошибок;
* проверку прав доступа.

### Integration-тесты

Проверяют взаимодействие приложения с сервером авторизации:

```text id="h3y6u8"
Приложение → Auth API → Ответ сервера
```

### End-to-end тесты

Проверяют полный пользовательский сценарий:

```text id="4c1w6n"
Открыть приложение
      ↓
Ввести данные
      ↓
Войти
      ↓
Открыть защищенную страницу
      ↓
Выйти
```

Такие тесты желательно запускать и для web, и для mobile.

## 7. Что делать, если нашли ошибку

Если после обновления библиотеки web-приложение работает, а mobile перестал выполнять вход, нужно сравнить поведение старой и новой версии библиотеки.

Также нужно проверить:

* изменения API;
* формат токена;
* настройки авторизации;
* обработку ошибок;
* совместимость старой версии клиента с новой библиотекой.

## Итог

После изменения общей библиотеки авторизации нужно провести регрессионное тестирование всех основных сценариев. Особое внимание нужно уделить web- и mobile-приложениям, потому что одна ошибка в общей библиотеке может повлиять сразу на несколько систем.
