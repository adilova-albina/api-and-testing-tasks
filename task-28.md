# Задание 28 - Тестирование создания заказа

Нужно протестировать endpoint, который создает новый заказ. При создании заказа система должна проверить данные, наличие товаров и сохранить заказ в базе данных.

## 1. Успешное создание заказа

Сначала проверяем основной позитивный сценарий.

```text
1. Отправить корректный запрос
2. Проверить данные заказа
3. Проверить наличие товаров
4. Создать заказ
5. Сохранить его в базе данных
6. Вернуть ответ клиенту
```

Пример запроса:

```json
{
  "userId": 15,
  "items": [
    {
      "productId": 101,
      "quantity": 2
    }
  ]
}
```

Ожидаемый результат:

* сервер возвращает `201 Created`;
* заказ получает свой `id`;
* заказ появляется в базе данных;
* количество товара на складе уменьшается.

## 2. Проверка некорректных данных

Нужно проверить, что сервер не создает заказ, если данные неправильные.

Например:

| Ситуация                    | Ожидаемый результат         |
| --------------------------- | --------------------------- |
| Нет `userId`                | `400 Bad Request` или `422` |
| Нет товаров                 | Ошибка валидации            |
| Товар не существует         | `404 Not Found`             |
| Некорректное количество     | Ошибка валидации            |
| Некорректный формат запроса | `400 Bad Request`           |

В таких случаях запись в базе данных создаваться не должна.

## 3. Товара нет на складе

Отдельно нужно проверить ситуацию, когда пользователь заказывает больше товара, чем есть на складе.

Например:

```text
На складе: 3 товара
Пользователь заказывает: 5
```

Ожидаемый результат:

```text
Заказ не создается.
Сервер сообщает, что товара недостаточно.
```

Например, можно вернуть `409 Conflict`.

Количество товара на складе при этом не должно измениться.

## 4. Проверка базы данных

После успешного создания заказа нужно проверить базу данных.

Например:

```text
До запроса:
Товар: 10 штук

Заказано:
3 штуки

После запроса:
Товар: 7 штук
Заказ создан
```

Это важно, потому что одного ответа API недостаточно. Нужно убедиться, что данные действительно сохранились.

## 5. Ошибка базы данных

Нужно проверить, что произойдет, если во время создания заказа возникнет ошибка базы данных.

В таком случае заказ не должен сохраниться частично.

Например:

```text
Создание заказа
      ↓
Проверка товара
      ↓
Изменение количества товара
      ↓
Ошибка при сохранении заказа
      ↓
Откат изменений
```

Для этого используется транзакция.

Если одна часть операции завершилась ошибкой, изменения должны быть отменены.

## 6. Integration-тест

Для этого endpoint хорошо подходит integration-тест, потому что нужно проверить сразу несколько компонентов:

```text
API
 ↓
Проверка данных
 ↓
База данных
 ↓
Склад
 ↓
Ответ клиенту
```

Например:

```text
Отправить POST /api/orders
        ↓
Проверить статус 201
        ↓
Проверить ID заказа
        ↓
Проверить запись в БД
        ↓
Проверить изменение остатка товара
```

## 7. Основные тестовые случаи

| № | Сценарий                | Ожидаемый результат           |
| - | ----------------------- | ----------------------------- |
| 1 | Корректный заказ        | `201 Created`                 |
| 2 | Пустой список товаров   | Ошибка                        |
| 3 | Несуществующий товар    | `404 Not Found`               |
| 4 | Недостаточно товара     | `409 Conflict`                |
| 5 | Некорректное количество | Ошибка валидации              |
| 6 | Ошибка БД               | Заказ не сохраняется частично |
| 7 | Успешный заказ          | Остаток товара обновляется    |

## Итог

Для создания заказа нужно проверить как успешные, так и ошибочные сценарии. Важно проверить не только HTTP-ответ, но и состояние базы данных и остаток товаров. Для этого лучше использовать integration-тесты. При ошибке во время операции изменения должны откатываться с помощью транзакции.
